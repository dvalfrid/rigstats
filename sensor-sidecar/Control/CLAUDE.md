# sensor-sidecar/Control — Control Center service side

Loaded when working in this folder. Everything here runs as **LocalSystem** and writes to real hardware (Super I/O fan registers, the AMD SMU, GPU drivers, HID lighting devices). Design, protocol and phase notes: `docs/control-architecture.md`.

## Safety rules for hardware writes

- **One way in.** Hardware is written only by an `IControlProvider`, driven by `ControlBroker` (apply, `preview` with auto-revert, `confirm`). Nothing else writes to hardware.
- **Clamp in the service, at write time.** Never trust a value from the pipe. Fan duty is clamped to the header's probed min/max in `FanProvider` on every write; CPU limits to `[floor, BIOS baseline]` (they can only lower); Curve Optimizer to its Min/Max; the GPU power limit to the adapter's own range.
- **Arm before a risky write.** CPU limits and Curve Optimizer call `BootCrashGuard.Arm()` *before* writing, so a crash mid-change leaves the marker and the next boot stays at BIOS values.
- **Always a way back.** Every provider implements `ReleaseToFirmware()` — best-effort, never throws. `SafetyGuard` calls it on service stop and `Program.cs` from a top-level `finally`.
- **Only verified hardware.** SMU access only on PM table versions known to `AmdSmuMap.Layout` and command ids verified per CPU generation; anything else is not offered (log the table head for a future fixture). Lighting models have `Verified` flags that drive `docs/supported-devices.md`.
- **Never probe with unknown commands.** Send only documented/observed command numbers to a device — not even a "get". A command sweep once broke a keyboard (Falchion Ace HFX).
- **Fans:** the critical-temperature override (100 %) lives in `FanCurveLoop` and must stay ahead of any curve; `FanWatchdog` hands fans back and fails fast if the loop stalls. Fan channels are mapped to fans only by measured identify results, never by name.
- **Pipe:** new methods go in `ControlPipeWorker.DispatchAsync`, behind `PipeClientVerifier`. Never take a file path from a client. A `BackgroundService` must not throw out of `ExecuteAsync` (it stops the whole host) — catch, log, back off.
- **Data folder:** anything read from `%ProgramData%\se.codeby.rigstats` is trusted only because `DataDirectory.EnsureSecure` ran first. Secrets (Hue key) are DPAPI-encrypted.

## Testing without hardware

Claude never runs anything against real hardware. Tests use fakes behind interfaces (`FakeFanHeader`, `IPawnIoModule`, `ILightingDevice`); `--dry-run` makes applies log-only. Live testing is done by the owner with `tools\dev-sidecar.ps1 -Live` in an elevated window — see "Live testing on real hardware" in `docs/control-architecture.md`. For new lighting devices run `/add-lighting-device`, for new providers `/add-control-provider`. A new `.cs` file must also be added to the `<Compile Include=…>` list in `sensor-sidecar.Tests/sensor-sidecar.Tests.csproj`.

## What lives here

`ControlBroker` incl. preview/auto-revert, `BootCrashGuard`, `FanProvider`, `FanCurveLoop`, `PowerPlanProvider`, `CpuLimitProvider` + `RyzenSmu`/`AmdSmuMap` — AMD PPT/TDC/EDC via LHM's signed RyzenSMU PawnIO module, only on hardware-verified PM table versions; `CurveOptimizerProvider` — AMD Curve Optimizer −30…0 through the same SMU, per-core only when the SMU's cores match Windows' physical cores; `GpuPowerProvider` + `AdlxGpuPower` / `NvmlGpuPower` (combined by `GpuPowerApis`) — GPU power limit via ADLX vtables (AMD) or NVML (NVIDIA desktop; laptop GPUs skipped, firmware-owned), back to the pre-RIGStats value, factory reset when it was at factory; `Lighting/` — `LightingProvider` (Aura Sync over `ILightingDevice`s; native protocols only, current hardware; `Rescan` finds devices plugged in or switched while running; `ToggleLamp` for the tray): `AuraController`/`AuraUsb` (ASUS Aura USB motherboard), `AsusMonitorDevice` (Aura monitors + light bar, incl. its desk lamp via `ILampDevice`), `LightingCatalog` (generates `docs/supported-devices.md` and the website's device table from the model tables' `Verified` flags; `SupportedDevicesTests` fails on drift — regenerate with `RIGSTATS_UPDATE_SUPPORTED_DEVICES=1`), `AsusKeyboardDevice` (ASUS TUF-protocol keyboards, ROG Omni receiver), `AsusHeadsetDevice` (GearLink-protocol headsets, read-back verified), `LampArrayDevice` (any HID LampArray / Dynamic Lighting device; the ROG Omni receiver's LampArray is its paired mouse — `OmniMouse` names it from the receiver's paired list and reads/switches its WDL mode, #236), `HueLink`/`HueBridge`/`HueRoomDevice` (Philips Hue rooms/zones via the Hue Bridge's local CLIP v2 API, #215 — paired from the Lighting tab, key DPAPI-encrypted in `hue.json`, TLS pinned to Hue's root CAs + bridge id; animations are slow 2 s fades because of the bridge's ~1 cmd/s limit), `SoftwareEffect` (service-drawn effects), `HidDevice`; ASUS Aura USB controllers (zones from the controller's own config table, every known controller id, yields to Armoury Crate; fixtures in `sensor-sidecar.Tests/fixtures/aura/`); `PeripheralBatteryMonitor` + `Lighting/Battery.cs` (`IBatteryDevice`, `BatteryReplies` — battery of wireless lighting devices into the telemetry, read-only, #290; each type's `QueryBattery` sends only its own documented question, pinned by `BatteryQueryTests`; `Connection.Of` classifies usb / bluetooth / 2.4ghz from the HID path and name, no device command)
