# sensor-sidecar/Control — Control Center service side

Loaded when working in this folder. Everything here runs as **LocalSystem** and writes to real hardware (Super I/O fan registers, the AMD SMU, GPU drivers, HID lighting devices). Design, protocol and phase notes: `docs/control-architecture.md`.

## Safety rules for hardware writes

- **One way in.** Hardware is written only by an `IControlProvider`, driven by `ControlBroker` (apply, `preview` with auto-revert, `confirm`). Nothing else writes to hardware.
- **Clamp in the service, at write time.** Never trust a value from the pipe. Fan duty is clamped to the header's probed min/max in `FanProvider` on every write; CPU limits to `[floor, BIOS baseline]` (they can only lower); Curve Optimizer to its Min/Max; the GPU power limit to the adapter's own range.
- **Arm before a risky write.** CPU limits and Curve Optimizer call `BootCrashGuard.Arm()` *before* writing, so a crash mid-change leaves the marker and the next boot stays at BIOS values.
- **Always a way back.** Every provider implements `ReleaseToFirmware()` — best-effort, never throws. `SafetyGuard` calls it on service stop and `Program.cs` from a top-level `finally`.
- **Only verified hardware.** SMU access only on PM table versions known to `AmdSmuMap.Layout` and command ids verified per CPU generation; anything else is not offered (log the table head for a future fixture). Lighting models have `Verified` flags that drive `docs/supported-devices.md`.
- **Never probe with unknown commands.** Send only documented/observed command numbers to a device — not even a "get". A command sweep once broke a keyboard (Falchion Ace HFX).
- **Fans:** the critical-temperature override (100 %) lives in `FanCurveLoop` and must stay ahead of any curve; `FanWatchdog` restarts the hardware worker if the loop stalls, and only after two restarts within two minutes hands the fans back and fails the service (#374). Fan channels are mapped to fans only by measured identify results, never by name.
- **Third-party native code runs out of process.** A native fault in a vendor DLL ends the process it runs in and no .NET handler can catch it, so the service must never load one itself. The GPU driver libraries (ADLX, NVML) run in the GPU worker (`Providers/GpuWorker.cs`, `rigstats-sensor.exe --gpu-worker`, #370): a crash or hang there is logged with its exit code, explained in the GPU tab and remembered until a restart or a driver change, while the service keeps running. A new vendor SDK goes into a worker the same way; Windows' own DLLs (hid, setupapi, cfgmgr32, powrprof) may stay in process. LibreHardwareMonitor runs in the hardware worker (`Workers/HardwareWorker.cs`, `--hardware-worker`, #374) the same way, and is restarted after a crash or a hang.
- **A domain that is down doesn't cost the rest.** A provider that can't be used for a known reason throws `DomainUnavailableException` (`ControlProtocol.cs`); `ControlBroker` skips that domain and applies the rest of the profile. Every other exception still rolls the whole profile back — use it only where skipping is safe (the hardware keeps what it has).
- **Problems are `Problem`s.** A domain that is unavailable because something failed (a crashed driver, a refused device) reports `CapabilitySet.Problem` (`ControlProtocol.cs`: severity, title, message in plain words, actions — a download link, "Collect diagnostics…", a help page — and the technical detail); the app shows it the same way everywhere. A domain the PC simply lacks has only `Reason` and stays hidden. Pinned by `contract/control-capability-problem.json` on both sides.
- **Pipe:** new methods go in `ControlPipeWorker.DispatchAsync`, behind `PipeClientVerifier`. Never take a file path from a client. A background worker derives from `GuardedBackgroundService` (implement `RunAsync`), never `BackgroundService` directly: an exception out of `ExecuteAsync` stops the whole host, the base class logs it and starts the worker again (#378). Handle the failures you expect yourself; it is the backstop.
- **Start-up:** nothing slow before `host.Run()` and nothing resolved from the container before it — the service must connect to the service manager within 30 s, and building a provider opens hardware (#383). Slow one-off work goes in a `BackgroundStartupTask`.
- **Data folder:** anything read from `%ProgramData%\se.codeby.rigstats` is trusted only because `DataDirectory.EnsureSecure` ran first. Secrets (Hue key) are DPAPI-encrypted.

## Testing without hardware

Claude never runs anything against real hardware. Tests use fakes behind interfaces (`FakeFanHeader`, `IPawnIoModule`, `ILightingDevice`); `--dry-run` makes applies log-only. Live testing is done by the owner with `tools\dev-sidecar.ps1 -Live` in an elevated window — see "Live testing on real hardware" in `docs/control-architecture.md`. For new lighting devices run `/add-lighting-device`, for new providers `/add-control-provider`.

## What lives here
